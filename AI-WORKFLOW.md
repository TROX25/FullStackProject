# AI-assisted development workflow

## Tools and models

- **Claude Code**, running on **Claude Sonnet 5** (`claude-sonnet-5`), as the primary development agent for this repository — planning, writing code, running builds/tests, and writing this documentation.
- **Anthropic Claude API** (`claude-haiku-4-5-20251001` by default) is also the *product's own* AI feature — the natural-language search interpreter (`AnthropicQueryInterpreter`), entirely separate from the tool used to build the app.

## Project instructions / reusable context configured

- `CLAUDE.md` (repo root) — defines this repo's commit convention (`<type>: <short description>`, committed and pushed only when explicitly asked) and, after this build, a project-specific section covering the Clean Architecture layering rule, the dependency-direction constraint, and the build/test/migration commands (added as part of this work so future AI-assisted sessions in this repo follow the same conventions without re-deriving them).
- `.github/copilot-instructions.md` — defines the commit message format referenced by `CLAUDE.md`.
- No custom skills/agents/prompt library were built specifically for this repo beyond the standard Claude Code session; the plan itself (produced via Claude Code's plan mode) served as the working spec for the implementation phase.

## How work was divided

1. **Requirements and product decisions came from the human**, made explicit up front rather than left for the AI to guess silently: which portal to crawl (OLX.pl, with a fallback), which AI provider (Anthropic), which database (SQLite), how "AI-deep" the matching should be (structured criteria + deterministic scoring, no embeddings), and which CQRS library (MediatR). These were captured as explicit multiple-choice decisions before any code was written, specifically so the resulting architecture reflects real product judgement, not an AI's arbitrary default.
2. **Claude Code produced a written implementation plan** (project layout, domain model, crawler design, AI-search contract, testing plan, doc plan, build sequence) from those decisions, which was reviewed before implementation began.
3. **Claude Code executed the entire implementation**: all four backend layers, the OLX crawler, the Anthropic integration with its guardrails and fallback, the Angular frontend, the automated test suites, and this documentation set.
4. **The human is expected to review this code before submission and interview** — per the assignment's own instruction to "be ready to navigate the code without relying on AI during the call." The architecture decisions above were deliberately kept explicit and explainable (see `ARCHITECTURE.md`'s "Key decisions" table) specifically to make that review tractable.

## How AI output was verified, corrected, and tested

Nothing was accepted on faith — every layer was built, then actually run, not just compiled:

- **Continuous build/test gates**: after every meaningful chunk of code, `dotnet build`/`dotnet test` (and `npm test`/`ng build` for the frontend) were run before moving on. 46 .NET tests and 6 Angular tests pass at the time of writing.
- **Manual end-to-end verification, not just unit tests**: the backend was run directly (`dotnet run`) and exercised via `curl` for the full crawl → store → search flow. The frontend was run via `ng serve` and driven with a real headless Chromium browser (Playwright) to click through "Fetch listings" → type a query → view ranked results → expand "Why this matched" — with screenshots inspected, not just "it compiled."
- **A genuinely blocking environment constraint was discovered and documented, not glossed over**: the sandbox this was built in has no general outbound internet access (confirmed via direct `curl` tests to `olx.pl` and even `example.com`, both rejected by the environment's proxy policy). This directly limits how much the live OLX crawler could be verified — see `ASSUMPTIONS.md` for exactly what that means for the live crawl path, called out explicitly rather than silently assumed to work.

## Two concrete examples of catching and correcting AI-generated issues

**1. A real bug caught by manual verification, not by inspection.** The initial `ListingRepository.UpsertRangeAsync` implementation used EF Core's `EntityEntry.CurrentValues.SetValues(listing)` to update an already-stored listing on re-crawl. This looked correct and built cleanly, and the *first* crawl of a fresh database worked fine. But triggering a **second** crawl against already-populated data threw `InvalidOperationException: The property 'Listing.Id' is part of a key and so cannot be modified` — because every freshly-crawled `Listing` object gets its own new `Guid` at construction time, and `SetValues` refuses to copy a different key value onto a tracked entity. Worse, that exception then corrupted the shared `DbContext`'s change tracker badly enough that the *subsequent* attempt to mark the crawl run "Failed" also silently failed (an unobserved exception on a fire-and-forget background `Task`), leaving the run stuck reporting `"status": "Running"` forever. This was only found by actually re-triggering a crawl twice end-to-end (via `curl`, then reproduced deterministically) — a pure code-review pass would very plausibly have missed it, since the code "looked" like a standard EF Core upsert pattern. Fixed two ways: (a) added `Listing.WithId(Guid)` so the incoming object is re-keyed to match the tracked entity before `SetValues` is called, and (b) hardened `CrawlRunner` to write a failure status through a **fresh** DI scope, so a corrupted `DbContext` from a mid-crawl exception can never again leave a run stuck at "Running". A regression test (`ListingRepositoryTests.UpsertRangeAsync_SameSourceListingIdTwice_UpdatesInPlaceWithoutThrowing`) now locks this in.

**2. A design suggestion rejected before it was even implemented.** While setting up the OLX crawler's HTTP client, EF Core's SQLite provider raised `SQLite Error 14: unable to open database file` in a way that looked environment-specific. The first hypothesis reached for was "the sandbox's filesystem doesn't support SQLite's locking" and the fix under consideration was switching integration tests to EF Core's in-memory provider instead of real SQLite — which would have quietly *weakened* the test suite (the in-memory provider doesn't validate real SQL/constraint behavior the way SQLite does, and wouldn't have caught bug #1 above at all). Instead of taking that shortcut, the actual cause was tracked down by instrumenting the connection-string resolution directly: `WebApplicationFactory`'s `ConfigureAppConfiguration` override was being applied *after* `Program.cs`'s top-level statements had already eagerly read `IConfiguration.GetConnectionString(...)`, so the test override was silently never taking effect and the app was trying (and failing) to open a relative path that didn't exist under the test host's working directory. The real fix — setting configuration via environment variables, which *are* visible before `Program.cs` runs even under `WebApplicationFactory`'s in-process hosting — kept the integration tests on real SQLite, which is exactly what caught bug #1.

## Limitations, privacy, and cost considerations of the chosen AI approach

See `ASSUMPTIONS.md` for the full list; in summary: only the user's typed search query is ever sent to Anthropic (no listing data, no personal data); a small/fast model is used deliberately since criteria extraction is a bounded task; the app degrades gracefully (never hard-fails) with no key configured or if the API call fails; and the live OLX crawler specifically could not be verified against the real site from within this development sandbox, which is documented as an explicit, load-bearing limitation rather than hidden.
